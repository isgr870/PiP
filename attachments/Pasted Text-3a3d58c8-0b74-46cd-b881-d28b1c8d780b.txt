I'm going to be direct here because I don't want you accidentally exposing yourself or future users to financial losses.
Problem 1: Live execution is already possible
Your README provides instructions for executing a Binance market purchase.
Your Python code also contains a direct order-submission endpoint.
The MetaTrader script calls mt5.order_send().
These are not simulated transactions.
My recommendation: disable live execution by default and introduce an explicit paper-trading mode.
Before anyone uses PiP with real money, I would want:
Explicit trade confirmation.
A testnet or demo environment.
Account and instrument validation.
Position-size verification.
Duplicate-order protection.
Comprehensive order logging.
A hard execution kill switch.
The current code's size restrictions are useful, but they do not constitute a complete financial safety system.
Problem 2: Your gate uses hardcoded assumptions
Your Python file contains predefined spread values, session-pair lists, volatility estimates and currency factors.
For example, the volatility values are derived from EURUSD hourly ranges, with some other instruments using scaling factors. �
GitHub
This is acceptable for an experimental prototype if clearly documented.
However, it should not be presented as a live market-analysis engine.
A better future architecture would distinguish:
Historical assumptions.
Live market observations.
Calculated risk.
Trade eligibility.
Actual execution.
These should be independently testable components.
Problem 3: The gate and execution are separate
Your README describes the trading gate and the Binance/MetaTrader execution paths.
But from the inspected Python code, I cannot establish that every execution route is obligatorily controlled by the gate.
That is a major architectural question.
A user should not be able to bypass the risk controls simply by invoking the execution function directly.
This is precisely the kind of issue worth testing.
Problem 4: The repository needs a deeper security review
I could inspect the README, Python files and package manifest, but GitHub's directory pages did not expose all the application source to my browser inspection.
I therefore cannot certify the security of server/, src/, or migrations/auth/.
We need to examine:
Authentication.
Session management.
API key handling.
Database permissions.
Server-side validation.
Deployment configuration.
Dependency vulnerabilities.
I would not market this as production-ready financial software yet.
